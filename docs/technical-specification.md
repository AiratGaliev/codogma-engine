## 1. Назначение и продуктовая цель

Codogma Engine развивается из существующей браузерной IDE в самостоятельную, связную среду разработки 2D HTML5-игр. Сейчас проект использует Phaser 4.2.1 как игровой runtime и предоставляет визуальное редактирование сцен, ассетов и анимаций, генерацию кода, локальный сервер и инструменты MCP.

Долгосрочная цель — дать разработчику единый рабочий процесс: открыть проект, отредактировать сцену и ассеты, сгенерировать код, запустить игру, проверить её и подготовить сборку. В перспективе продукт должен получить собственную архитектуру редактора, устойчивые API расширений и удобную упаковку приложений.

Фраза «движок уровня Unity» может использоваться только как дальний ориентир по широте рабочего процесса. Она **не** означает обещание паритета с Unity, поддержки всех её платформ или функций. Направление развития оценивается по определённым требованиям и критериям приёмки этого проекта.

### 1.1. Критерии успеха

- Существующие проекты и основные сценарии редактирования продолжают работать в течение миграции.
- Форматы проекта и семантика сгенерированного кода сохраняют совместимость, если отдельное решение явно не вводит версионирование и миграцию.
- Архитектурные изменения вводятся по частям, имеют проверяемые границы и не требуют одномоментного переписывания редактора.
- Desktop-версия не требует от пользователя самостоятельно устанавливать Node.js для запуска основного приложения.
- Сборка, установка, обновление и дополнительные платформы документированы как реализованные только после фактической проверки.

## 2. Текущее состояние (as-is)

Сведения ниже описывают подтверждённую базовую реализацию, а не целевую архитектуру.

### 2.1. Основные компоненты

| Область | Текущее состояние |
|---|---|
| Сервер | `server/server.mjs` — локальный Node.js HTTP-сервер, API редактора/проекта, play mode и мост MCP |
| Редактор | TypeScript-клиент в `source/editor/`; workbench и части функциональности используют унаследованный каркас Colibri |
| Игровой runtime | Phaser 4.2.1, типы и адаптации, используемые компилятором и редактором |
| Файлы проекта | Сцены, префабы, пакеты ассетов, компоненты и другие форматы текущего редактора |
| MCP | Официальный пакет `@phaserjs/editor-mcp-server`, локальный мост и встроенные fallback-точки входа |
| AI Chat | Необязательный сервис в `mini-services/ai-chat/`; для базового запуска редактора не требуется |
| Тестирование | `npm run build`, серверный smoke test в CI и MCP-интеграционный тест `npm run test:e2e` |
| CI | `fast-checks` запускается на PR в `dev`, `test` и `main`; `mcp-integration` — на PR в `test` и `main` |
| Артефакт | Workflow на `main` формирует ZIP как GitHub Actions artifact. Сам по себе он не публикует GitHub Release и не является установщиком Tauri |

Порты по умолчанию: HTTP-сервер — 3000, MCP-мост — 1902, AI Chat — 3031. Они могут быть переопределены переменными окружения; это не жёсткие архитектурные контракты.

### 2.2. Текущие возможности

Базовая версия включает визуальный Scene Editor, prefabs, User Components, Asset Pack Editor, Animations Editor, Editable Tilemap, инструменты физики и эффекты Phaser, генерацию TypeScript-кода, а также MCP/AI-интеграцию. Подробности и ограничения конкретных подсистем указаны в [README](../README.md) и проверяются по реализации и тестам.

Наличие редакторского UI для технологии не гарантирует, что все необходимые runtime-зависимости уже упакованы в любой пользовательский игровой проект. Перед распространением игры нужно проверять сгенерированный код, зависимости runtime и итоговую сборку.

### 2.3. Базовые ограничения и известная работа

- Сервер и клиент пока зависят от браузерного HTTP workflow.
- Значительная часть редактора опирается на унаследованный workbench и плагины; реальный объём связанности нужно устанавливать инвентаризацией и тестами, а не только количеством файлов.
- Проект не следует считать готовым к desktop-дистрибуции, обновлению без сети или независимому runtime до прохождения соответствующих критериев приёмки.
- Статус «CI зелёный» означает прохождение существующих автоматических проверок, а не автоматическую приёмку всех визуальных сценариев редактора.

## 3. Целевой продукт и границы работ

### 3.1. Входит в целевое направление

1. Удобная работа с проектом и файлами, безопасный выбор каталога проекта и обнаружение внешних изменений.
2. Сохранение и редактирование сцен, префабов, ассетов, анимаций, тайлмапов и пользовательских компонентов.
3. Предсказуемая генерация кода и запуск игры из редактора.
4. Desktop-оболочка с нативными возможностями там, где это улучшает UX или безопасность.
5. Документированные API расширений после того, как соответствующие точки расширения стабилизируются.
6. Упаковка готовой игры и дополнительные runtime/платформы как отдельные будущие направления с собственными критериями приёмки.

### 3.2. Не входит в текущую миграцию без отдельного решения

- Полный паритет с Unity или другим универсальным игровым движком.
- Переписывание Phaser, разработка собственного 3D-runtime или сетевого multiplayer.
- Массовая замена зависимостей исключительно ради использования нового стека.
- Удаление работающей подсистемы только ради архитектурной чистоты, если замена не прошла проверку совместимости.
- Автоматическое удаление лицензионных уведомлений на основании переименования или перемещения исходников.

## 4. Архитектурное направление

### 4.1. Предварительная схема

Целевой путь рассматривается как постепенное отделение редакторского UI от проектных файлов и системных возможностей. Desktop-оболочка может быть реализована на Tauri 2, а новый UI — на Svelte 5; эти решения должны подтвердиться прототипом и сравнением затрат с альтернативами.

```
Codogma Engine
├─ Editor UI
│  ├─ текущий TypeScript/Colibri-клиент — сохраняется в период миграции
│  └─ новый workbench — поэтапно, после проверки прототипа
├─ Project Services / Contracts
│  ├─ выбор проекта и файловые операции
│  ├─ наблюдение за файлами
│  ├─ запуск игры и выдача файлов в play mode
│  └─ интерфейсы для MCP/AI и других инструментов
├─ Adapters
│  ├─ текущие HTTP API и Node.js server
│  └─ Tauri/Rust-реализация — по частям, при доказанной готовности
└─ Game Runtime
   └─ Phaser 4.2.1 в текущем направлении
```

Это схема границ ответственности, а не описание уже существующих модулей. Новые интерфейсы и адаптеры должны добавляться постепенно и оставаться полезными как для текущего браузерного приложения, так и для desktop-оболочки.

### 4.2. Статус технологических решений

| Решение-кандидат | Статус | Что проверить до окончательного выбора |
|---|---|---|
| Tauri 2 для desktop-оболочки | Основной кандидат | Упаковка на Windows, доступ к выбранному проекту, play mode, MCP bridge, безопасность и размер/время запуска |
| Существующий Node.js сервер как временный sidecar | Механизм первого PoC | Запуск без установленного пользователем Node.js, корректное завершение процесса, журналирование, порты и упаковка |
| Svelte 5 + Vite для нового UI | Кандидат | Прототип workbench, масштабируемость панелей, интеграция canvas-редакторов и цена постепенной миграции |
| dockview-core для панелей/вкладок | Кандидат | Layout persistence, keyboard navigation, доступность, лицензия и производительность на целевых сценариях |
| CodeMirror 6 вместо текущего редактора кода | Кандидат | Совместимость с языковыми функциями, расширениями, командами и пользовательскими сценариями |
| Rust/Tauri commands для системных операций | Целевое направление | Безопасные границы доступа, контрактные тесты, кроссплатформенность и объём поддержки |
| Переписывание MCP-моста и AI Chat на Rust | Не утверждено | Необходимость, совместимость протоколов и реальная выгода по сравнению с сохранением отдельного сервиса |

Не следует одновременно фиксировать все перечисленные зависимости и переписывать несколько подсистем. Каждый спорный выбор должен сначала иметь небольшой PoC и чёткий критерий решения.

### 4.3. Принципы миграции

1. **Сохранение поведения важнее сохранения конкретной реализации.** Перед заменой подсистемы зафиксировать её внешний контракт и тестируемые сценарии.
2. **Поэтапная миграция.** Новая реализация и старая могут сосуществовать за адаптером до успешной приёмки.
3. **Не переписывать форматы без необходимости.** При неизбежном изменении добавить версию формата, миграцию и тестовые fixtures.
4. **Не смешивать инфраструктурную и UI-миграцию.** Изменения вводить вертикальными срезами, чтобы регрессии можно было локализовать.
5. **Веб-режим сохраняется во время миграции.** Отказ от браузерного сценария — отдельное продуктовое решение, не случайное следствие использования Tauri.
6. **Никаких скрытых зависимостей от окружения.** Пути, порты, доступ к файлам и запуск подпроцессов должны иметь явные настройки, ошибки и тесты.

## 5. Обязательные требования

Требования ниже обязательны для соответствующего этапа. Конкретный этап, на котором каждое требование становится критерием релиза, указан в [roadmap.md](roadmap.md).

### 5.1. Совместимость и целостность данных

- **REQ-DATA-01.** Редактор открывает проекты текущего формата без ручного преобразования.
- **REQ-DATA-02.** Сохранение и повторное открытие сцены/префаба не теряют содержимое, порядок и поддерживаемые свойства.
- **REQ-CODE-01.** Генерация кода сохраняет семантику текущего компилятора; пользовательские секции, например `START-USER-*`, сохраняются в сценариях повторной компиляции, которые их поддерживают.
- **REQ-MIG-01.** Если совместимость нарушается осознанно, изменение сопровождается явным версионированием, миграцией, тестами и инструкцией. «Аддитивный» формат не гарантировать, если он мешает корректной модели данных.

### 5.2. Работа с проектом и runtime

- **REQ-PROJ-01.** Пользователь может выбрать каталог проекта и видеть понятную ошибку при отсутствии прав, недоступном пути или повреждённой структуре.
- **REQ-PROJ-02.** Изменения файлов вне редактора обрабатываются согласованно; watcher не должен приводить к повреждённому состоянию или бесконечным циклам перезагрузки.
- **REQ-PLAY-01.** После сохранения пользователь может запустить проект; корректно обслуживаются пути к ассетам и необходимые runtime-ресурсы.
- **REQ-PLAY-02.** Ошибки запуска и генерации кода доступны пользователю и разработчику через понятное сообщение/диагностику.
- **REQ-WEB-01.** Пока поддерживается браузерная версия, изменения desktop-адаптера не должны незаметно ломать её контракт.

### 5.3. Desktop, безопасность и обслуживание

- **REQ-DESK-01.** Установка и запуск основного desktop-приложения не требуют отдельной установки Node.js пользователем.
- **REQ-DESK-02.** Перед выпуском заявленные Windows/macOS/Linux-платформы реально собираются и проходят документированный smoke/acceptance test. Непроверенная платформа не считается поддержанной.
- **REQ-SEC-01.** Доступ к файловой системе ограничивается выбранным проектом и явно разрешёнными действиями. Нельзя использовать общий файловый доступ только ради удобства реализации.
- **REQ-SEC-02.** Вызов внешних процессов, загрузки обновлений и работы с секретами должен иметь явную границу доверия, обработку ошибок и документацию.
- **REQ-OFFLINE-01.** Базовые операции с локальным проектом после установки не должны зависеть от доступности сети; AI-функции и получение обновлений могут требовать сеть.
- **REQ-MCP-01.** Поддерживаемые MCP-инструменты сохраняют документированный контракт либо получают версионированную замену и тест миграции.

### 5.4. Производительность

Цели по скорости запуска и размеру проекта должны измеряться на воспроизводимой фикстуре и определённом тестовом окружении. Значения «проект на 1000 файлов за 3 секунды», «сцена на 500 объектов без просадок» и «холодный старт за 2 секунды» — пока **гипотезы для проверки**, а не подтверждённые свойства или обязательные release-gates.

До закрепления численных порогов необходимо:
1. создать или описать репрезентативные фикстуры;
2. определить, что именно измеряется (например, время до готового к взаимодействию UI, а не до открытия окна);
3. зафиксировать тестовую машину/условия и методику;
4. снять baseline текущей версии;
5. установить порог на основе измерений и обновлять его вместе с тестовой методикой.

## 6. Проверки и критерии готовности

Для каждой изменяемой подсистемы нужны критерии на уровне поведения, а не только успешная компиляция.

- Изменения TypeScript редактора: `npm run build` из корня после установки зависимостей корня и `source/editor`.
- Изменения сервера/MCP: запущенный сервер и `npm run test:e2e` с описанием результата.
- Изменения визуального редактора, генерации кода, play mode или Tauri: ручной браузерный/desktop-сценарий, соответствующий изменению; MCP E2E не заменяет UI-приёмку.
- Продвижение в `test`/`main`: обязательные CI-статусы `fast-checks` и `mcp-integration` должны проходить на целевой ветке.
- Изменения форматов/миграций: тесты открытия, сохранения, повторного открытия и компиляции на фиксированных проектах.

В PR должны быть указаны команды и результаты. Проверки, которые не запускались, нужно назвать прямо. Красный CI исправляется по причине; отключение проверки или ослабление теста не является критерием готовности.

Фаза дорожной карты закрывается только после выполнения её критериев целиком, но работа внутри фазы должна идти небольшими независимыми PR.

## 7. Лицензии и происхождение кода

В проекте присутствует код, производный от открытого исходного кода Phaser Editor 2D v3. Переименование продукта, перенос файлов или замена UI-оболочки сами по себе не отменяют требований к уведомлениям, лицензиям и атрибуции.

- Сохранять все применимые upstream-уведомления и лицензии в исходниках, дистрибутивах и файлах документации.
- Не удалять копирайт Arian Fornaris или другие upstream-уведомления только потому, что Colibri удалён или переименован.
- Изменять лицензирование и атрибуцию можно только после документированного аудита происхождения кода и подтверждения, что изменения соответствуют применимым лицензиям.
- Для новых зависимостей фиксировать версии и проверять лицензионные условия перед распространением.

## 8. Основные риски

| Риск | Мера снижения |
|---|---|
| Скрытая связанность UI, файлового API и моделей Colibri | Инвентаризация контрактов и постепенное выделение адаптеров; не переписывать Scene Editor первым |
| Tauri ломает текущий HTTP/origin workflow, play mode или MCP bridge | PoC с реальным fixture-проектом и проверкой всех этих путей до начала массовой миграции |
| Слишком раннее фиксирование набора UI-зависимостей | Проверять Svelte/workbench/CodeMirror малым прототипом и документировать решение |
| Регрессии сохранения и компиляции | Golden/fixture-тесты старого и нового пути до миграции подсистем |
| Избыточная перепись сервера в Rust | Мигрировать только обоснованные system-facing функции; оставить сервисы на Node там, где это снижает риск и не мешает продуктовым требованиям |
| Desktop доступен к произвольным файлам или запускает неожиданные процессы | Узкая файловая область, явный выбор проекта, проверка разрешений и сценарии негативного тестирования |
| Ошибочная оценка лицензионного статуса после рефакторинга | Сохранять уведомления до документированного source/license audit |

## 9. Глоссарий

- **Colibri** — унаследованный редакторский workbench и связанная инфраструктура.
- **PoC (proof of concept)** — небольшой прототип для проверки риска или технологического решения до масштабной реализации.
- **Adapter** — слой, позволяющий одной подсистеме использовать разные реализации одного контракта.
- **MCP** — Model Context Protocol, протокол инструментов для AI-клиентов.
- **Play mode** — запуск редактируемого игрового проекта из редактора.
- **Fixture** — зафиксированный тестовый проект/набор входных файлов для воспроизводимых проверок.
