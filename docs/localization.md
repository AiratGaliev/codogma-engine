# Локализация Codogma Engine: таблицы, fallback и диагностика

Статус: реализовано в рамках задачи **COD-62** («Реализовать localization tables и fallback для разных языков», Этап 5 — 2D authoring tools, P1).

Поддержка localization вынесена из общей проверки lifecycle в отдельный проверяемый backlog item. Реализация — минимальный, опциональный модуль `@codogma/localization` в [`packages/localization/`](../packages/localization/); она не делает локализацию обязательной для минимальной игры и не переписывает существующие текстовые ресурсы редактора.

## 1. Что реализовано

- Версионированный контракт localization tables (schema version 1) для таблиц и локализуемых строк.
- Runtime-сервис: получение текста по стабильному ключу, переключение активной локали, подстановка именованных параметров, детерминированный fallback.
- Структурированная диагностика (`LocalizationDiagnostic`) с кодами проблем и дедупликацией.
- Валидация таблиц: некорректный JSON, отсутствующая/неподдерживаемая версия, дублирующиеся ID, некорректные записи, расхождения ключей и несовпадающие placeholders между локалями.
- Фикстура в тестовом проекте и автоматические проверки: unit/contract tests + acceptance-проверка на работающем сервере.

## 2. Контракт таблиц (schema version 1)

Таблица — JSON-файл одной локали. Размещение в игровом проекте:

~~~text
<проект игры>/
└── locale/
    ├── en-US.json
    ├── ru-RU.json
    └── en-GB.json
~~~

Формат:

~~~json
{
    "schemaVersion": 1,
    "locale": "en-US",
    "messages": [
        { "id": "menu.play", "text": "Play" },
        { "id": "profile.welcome", "text": "Hello, {name}!" }
    ]
}
~~~

| Поле / правило | Требование |
|---|---|
| `schemaVersion` | Обязателен. Поддерживается только `1`. Отсутствующая или неизвестная версия — ошибка `LOC_MISSING_VERSION` / `LOC_UNSUPPORTED_VERSION`; данные никогда не трактуются молча как текущая версия. |
| `locale` | Обязателен. Упрощённый BCP 47: язык и опциональные `-`-подтеги (`ru`, `en-US`, `pt-BR`, `zh-Hans`). Форма с `_` (`ru_RU`) отклоняется с подсказкой. |
| `messages` | Обязателен. **Массив явных записей** `{ id, text }`, а не JSON-объект. |
| `id` | Некоторый стабильный ключ без пробелов (`menu.play`, `player.health`). Одинаков во всех локалях. |
| `text` | Непустая строка перевода; может содержать placeholders `{name}`. |

**Почему явные записи, а не объект.** Для формы `"messages": { "menu.play": "Play" }` стандартный `JSON.parse` теряет информацию о дубликатах ключей (остаётся последнее значение). Форма с массивом записей позволяет валидатору обнаружить дубликаты ID по разобранным данным; объектная форма отклоняется диагностикой `LOC_INVALID_MESSAGES`, а не интерпретируется молча.

**Placeholders.** Грамматика contract v1: `{name}`, где имя начинается с буквы/подчёркивания и продолжается буквами, цифрами или подчёркиваниями. Всё остальное в фигурных скобках — литеральный текст. Сложные правила множественного числа и ICU MessageFormat **не входят** в контракт v1.

**Версии.** Валидатор отклоняет неизвестные версии с понятной ошибкой. Система миграций будущих форматов в этом scope не создаётся: при появлении версии 2 добавляется явное правило миграции и тесты.

## 3. Runtime API

Скомпилированный модуль (`packages/localization/dist/index.js`, ESM, без зависимостей) работает и в браузере игры, и в Node (валидация, тесты, tooling).

~~~js
import { LocalizationService, parseLocalizationTable } from "@codogma/localization"

// 1. Загрузить и разобрать таблицы (браузер: fetch; Phaser: this.load.json)
const en = parseLocalizationTable(await (await fetch("locale/en-US.json")).text(), "locale/en-US.json")
const ru = parseLocalizationTable(await (await fetch("locale/ru-RU.json")).text(), "locale/ru-RU.json")

// 2. Создать сервис: таблицы, активная локаль, fallback
const service = new LocalizationService({
    tables: [en.table, ru.table],
    locale: "en-US",
    fallbackLocale: "en-US"
})

// 3. Получать локализованный текст
service.t("menu.play")                            // "Play"
service.t("profile.welcome", { name: "Alex" })    // "Hello, Alex!"

service.setLocale("ru-RU")                        // переключение активной локали
service.t("profile.welcome", { name: "Алексей" }) // "Привет, Алексей!"

// 4. Диагностика проекта
service.getDiagnostics()                          // дедуплицированный список
service.clearDiagnostics()
~~~

Полную таблицу API и пример интеграции см. в `packages/localization/README.md`.

### Ключевые правила API

| Метод | Поведение |
|---|---|
| `t(id, params?)` | Активная локаль → fallback-локаль → маркер `[[id]]`. Никогда не бросает исключение. |
| `setLocale(locale)` | Неизвестная локаль отклоняется: диагностике `LOC_UNKNOWN_LOCALE` и сохранение предыдущей локали. Переключение не меняет сериализованные данные проекта. |
| `registerTable(table)` | Добавляет таблицу загруженной позже локали (например, лениво загруженный язык). Если это настроенная fallback-локаль — fallback включается автоматически. Повторная регистрация той же локали игнорируется с warning `LOC_DUPLICATE_REGISTRATION`: сохраняется первая таблица. |
| `getDiagnostics()` / `clearDiagnostics()` | Дедупликация по `code + locale + messageId`; очистка сбрасывает и память дедупликации. |

## 4. Fallback: детерминированные правила

1. Ключ ищется в таблице активной локали.
2. При отсутствии — в настроенной fallback-локали (если задана и зарегистрирована); выдаётся диагностика `LOC_FALLBACK_USED` (warning). Проверка «зарегистрирована» выполняется при каждом запросе: таблицу fallback можно зарегистрировать позже через `registerTable` — fallback начнёт работать без пересоздания сервиса.
3. При отсутствии и там — возвращается видимый маркер `[[<id>]]` и диагностика `LOC_MISSING_TRANSLATION` (warning).
4. Некорректная таблица (ошибка структуры, версии, дубликатов ID) **отклоняется парсером** и не регистрируется: её содержимое никогда не выдаётся за корректный перевод.
5. Параметр, отсутствующий в вызове, остаётся видимым в тексте (`Hello, {name}!`) с диагностикой `LOC_MISSING_PARAM` (warning).
6. Автоматический переход по префиксу (например, `pt-BR` → `pt`) **не выполняется неявно**. Такой переход допускается только как явная часть контракта будущих версий с тестами.

Одинаковые настройки и данные всегда дают одинаковый результат (проверено тестом детерминизма).

## 5. Валидация и диагностика

`validateLocalizationProject(tables, { fallbackLocale })` выполняет кросс-локальные проверки разобранных таблиц. Правила:

| Проверка | Код | Серьёзность | Продолжение работы |
|---|---|---|---|
| Файл не JSON | `LOC_PARSE_ERROR` | error | таблица не загружается; известна строка/колонка, когда парсер их сообщает |
| Нет `schemaVersion` | `LOC_MISSING_VERSION` | error | таблица не загружается |
| Неизвестная версия | `LOC_UNSUPPORTED_VERSION` | error | таблица не загружается |
| Некорректный тег локали | `LOC_INVALID_LOCALE` | error | таблица не загружается |
| `messages` не массив записей | `LOC_INVALID_MESSAGES` | error | таблица не загружается |
| Некорректная запись (нет `id`/`text`) | `LOC_INVALID_ENTRY` | error | таблица не загружается |
| Пустой ID / пробелы в ID | `LOC_INVALID_ID` | error | таблица не загружается |
| Пустой текст | `LOC_INVALID_TEXT` | error | таблица не загружается |
| Дубликат ID в таблице | `LOC_DUPLICATE_ID` | error | таблица не загружается (сохраняется первое вхождение, детерминированно) |
| Дубль локали в проекте | `LOC_DUPLICATE_LOCALE` | error | проект не проходит валидацию |
| Fallback без таблицы | `LOC_UNKNOWN_FALLBACK_LOCALE` | error | проект не проходит валидацию; runtime: warning, fallback неактивен, пока таблица не зарегистрирована, после регистрации работает |
| Повторная регистрация таблицы той же локали | `LOC_DUPLICATE_REGISTRATION` | warning | сохраняется первая таблица |
| Ключ отсутствует в локали относительно reference | `LOC_MISSING_KEY` | warning | продолжается, используется fallback |
| Ключ есть только в не-reference локали | `LOC_EXTRA_KEY` | warning | продолжается, ключ не используется, пока его нет в reference |
| Placeholders различаются между локалями | `LOC_PLACEHOLDER_MISMATCH` | error | валидация сообщает ошибку; runtime использует перевод как есть — параметр, отсутствующий в вызове, остаётся видимым в тексте с диагностикой `LOC_MISSING_PARAM` |
| Неизвестный ключ при запросе | `LOC_MISSING_TRANSLATION` | warning | маркер `[[id]]` |

**Reference-локаль** выбирается детерминированно: настроенная fallback-локаль, иначе локаль с наибольшим числом ключей (при равенстве — лексикографически первая).

**Куда поступает диагностика.** В текущем baseline репозитория нет отдельной панели project-diagnostics (см. `docs/capability-matrix.md`), поэтому модуль отдаёт структурированные объекты `LocalizationDiagnostic` (код, серьёзность, локаль, ID строки, путь к таблице, сообщение). Потребители:

- автоматические тесты (`npm run test:localization`) проверяют точные коды и серьёзность;
- acceptance-проверка (`npm run test:localization:acceptance`) выводит сводку при прогоне;
- подключение к редакторской диагностике проекта — отдельный follow-up через небольшой адаптер (в этом PR не выполнялось).

Дедупликация гарантирует, что повторное получение одного отсутствующего перевода не создаёт бесконечный поток одинаковых сообщений.

## 6. Интеграция с игрой: ключ отдельно от отображаемого текста

Требование ТЗ: хранить ключ локализации отдельно от текущей отображаемой строки. Минимальный путь для игровой логики — использовать сервис в пользовательском компоненте/сцене и вычислять видимый текст в runtime:

~~~js
// пользовательский скрипт игры (TypeScript или JS)
import { LocalizationService } from "@codogma/localization"

// сервис создаётся один раз при старте игры из таблиц проекта
label.setText(localization.t("menu.play"))
~~~

В рамках COD-62 сериализация сцен и текстовые компоненты редактора **не изменялись**: текстовый объект по-прежнему хранит отображаемый текст как раньше. Добавление локализуемых свойств в компоненты Scene Editor (например, `localizationKey`) — отдельная задача после принятия этого контракта; существующее хранение данных не затронуто и не ломается.

## 7. Фикстура и проверки

### Фикстура проекта

`tests/workspace/test-typescript/locale/`:

| Файл | Содержимое |
|---|---|
| `en-US.json` | Полный набор: `menu.play`, `menu.settings`, `profile.welcome {name}`, `score.display {score}`. |
| `ru-RU.json` | Полный набор тех же ключей с русским текстом (UTF-8). |
| `en-GB.json` | Специально урезанная таблица (только `menu.play`) для проверки fallback и диагностики недостающих ключей. |

Фикстурные таблицы структурно валидны; намеренно некорректные таблицы находятся в `packages/localization/tests/fixtures/` (сломанный JSON, нет версии, версия 2, дубликат ID, объектная форма, `ru_RU`, некорректные записи/ID/текст).

### Команды

~~~bash
# сборка + unit/contract/validation/fixture tests (node:test)
npm run test:localization

# runtime acceptance: поднимает сервер, забирает таблицы через /editor/external/,
# прогоняет реальный скомпилированный сервис
npm run test:localization:acceptance
~~~

Обе команды входят в CI Fast как шаги «Build and test localization package» и «Localization runtime acceptance».

### Чек-лист проверенного поведения

| Сценарий | Где проверено |
|---|---|
| Один ключ → текст en-US и ru-RU | `fixture.test.mjs`, acceptance |
| Подстановка параметров, типы значений | `service.test.mjs`, acceptance |
| Отсутствующий перевод → fallback + диагностика | `service.test.mjs`, acceptance |
| Отсутствующая локаль → явная политика (отказ, без случайного выбора) | `service.test.mjs` |
| Дубли ID → обнаружение до использования таблицы | `contract.test.mjs` |
| Сломанные данные (JSON/версия/типы) без необработанных падений | `contract.test.mjs` |
| Несогласованные ключи между локалями | `validation.test.mjs`, acceptance |
| Несовпадающие placeholders | `validation.test.mjs` |
| UTF-8 (русский/английский) через HTTP и runtime | `fixture.test.mjs`, acceptance |
| Стабильность диагностики (нет потока дублей) | `service.test.mjs`, acceptance |
| Детерминизм повторных прогонов | `service.test.mjs`, `validation.test.mjs` |

## 8. Ограничения и не заявленные возможности

Следующие возможности **не заявляются поддерживаемыми** в рамках этой задачи (ТЗ, раздел 9.2):

- **RTL и сложный text shaping** — не проверены на конкретном text/rendering backend; подключение шрифтов с RTL-скриптами остаётся ответственностью игры.
- **ICU MessageFormat, плюрализация, селекторы** — вне грамматики contract v1.
- **Fallback fonts и UTF-8 glyph coverage** конкретного шрифта — проверяются отдельно; модуль только передаёт строки текстовому backend.
- **Автоматическое изменение длины строк / layout-адаптация** — не входит.
- **Миграции версий таблиц** — v1 отклоняет иные версии; правило миграции появится вместе с v2.
- **Редакторский UI для перевода** (визуальный редактор таблиц) — не входит; таблицы редактируются как обычные файлы проекта.
- **Машинный перевод, интеграция внешних сервисов, workflow переводчиков** — не входит.
- **Подключение диагностики к панели проекта редактора** — отдельный follow-up; сейчас диагностика потребляется тестами/CLI-прогоном.
