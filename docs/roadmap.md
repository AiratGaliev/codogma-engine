# Дорожная карта: Codogma Engine

Документ переводит продуктовое направление и требования из [технического задания](technical-specification.md) в проверяемые этапы. Это план развития, а не обещание паритета с Unity и не утверждение, что перечисленные технологии уже используются.

**Текущая база:** браузерная IDE с локальным Node.js-сервером, Phaser 4.2.1, генерацией игрового кода, MCP-инструментами и необязательным AI Chat. **Следующий шаг — доказать жизнеспособность desktop-оболочки на реальном проекте, а не переписать весь код разом.**

## Как вести roadmap

1. Разбивать крупный этап на небольшие задачи и отдельные PR в `dev`. Один PR должен описывать одну логически завершённую задачу, а не переносить целый этап целиком.
2. Не считать чекбокс выполненным по факту наличия кода или успешной сборки: закрывать его только после проверки соответствующего критерия приёмки.
3. Завершение этапа означает, что выполнены все его критерии и связанные тесты. Незавершённые задачи могут разрабатываться в отдельных topic-ветках, но этап нельзя объявлять завершённым частично.
4. При изменении границ этапа, требований, форматов или принятых архитектурных решений обновлять этот файл и [техническое задание](technical-specification.md) в том же PR.
5. Обновлять `CHANGELOG.MD` для пользовательски значимых изменений и релизных milestones. Не превращать журнал изменений в список незаконченных внутренних задач.
6. Перед удалением старой реализации доказать, что новая покрывает её контракт. Если неясна необходимость или цена технологии, сначала сделать PoC и принять решение по его результатам.
7. Не считать удаление унаследованного кода или упоминаний самоцелью. Сохранять применимые лицензии и upstream-уведомления; вопрос атрибуции решать только по результатам документированного аудита происхождения кода.

## Этап 0 — зафиксировать рабочую базу v1.0

**Статус: выполнено на уровне текущей базовой версии.** Это точка сравнения для следующих этапов, а не подтверждение готовности всех будущих desktop-функций.

- [x] Брендинг Codogma Engine и версия продукта 1.0.
- [x] Локальный сервер в `server/server.mjs`, который обслуживает редактор и API проекта.
- [x] Интеграция Phaser 4.2.1, типы и генерация игрового кода.
- [x] Существующие инструменты редактирования сцен, префабов, ассетов, анимаций и тайлмапов; поддерживаемые интеграции физики и эффектов.
- [x] MCP-интеграция через мост и встроенные fallback-точки входа.
- [x] Опциональный AI Chat сервис.
- [x] GitHub Actions: fast checks, MCP integration для PR в `test`/`main`, ZIP artifact для `main`.

**Критерии базовой версии:**
- [x] Команды установки, сборки и запуска описаны в README.
- [x] CI умеет собирать редактор и запускать smoke test сервера.
- [x] Известны границы текущих проверок: обычный PR в `dev` не запускает интеграционный MCP E2E автоматически, UI acceptance требует отдельных проверок.
- [x] Release workflow публикует артефакт GitHub Actions, но пока не выпускает GitHub Release и не собирает Tauri-установщик.

## Этап 1 — desktop PoC на Tauri 2

**Цель:** проверить, можно ли надёжно упаковать существующий редактор для Windows без переписывания редакторского клиента и backend.

**Зависимости:** этап 0.

### Задачи

- [ ] Добавить минимальный Tauri 2 shell и зафиксировать версии инструментов сборки.
- [ ] Запустить текущий сервер как упакованный sidecar или выбрать другой подтверждённый способ запуска; пользователь не должен отдельно устанавливать Node.js.
- [ ] Открыть текущий editor UI в webview, не меняя форматы проекта и кодогенерацию.
- [ ] Проверить выбор и открытие реального fixture-проекта, сохранение сцены, компиляцию, play mode и пути к ассетам.
- [ ] Проверить MCP bridge и завершение фоновых процессов при закрытии приложения.
- [ ] Проверить Windows-сборку и запуск на чистой машине/окружении без установленного Node.js.
- [ ] Зафиксировать ограничения и решение по результатам PoC: продолжать с Tauri, изменить механизм sidecar или пересмотреть оболочку.

### Критерии приёмки

- [ ] Упакованное приложение запускается без предварительной установки Node.js.
- [ ] Fixture-проект проходит полный smoke-сценарий: открыть → изменить/сохранить сцену → сгенерировать код → запустить play mode → закрыть и открыть снова.
- [ ] Работа с локальными файлами и запуск игрового preview корректны в webview; ошибки отображаются диагностируемо.
- [ ] Фоновый сервер/sidecar не остаётся работать после закрытия приложения.
- [ ] Зафиксированы ограничения прототипа, выбранный путь упаковки и решения, требующие отдельного исследования.

**Gate:** если PoC обнаруживает блокирующие ограничения, не переходить к массовой миграции: уточнить архитектуру и критерии этого этапа.

## Этап 2 — границы доступа к проекту и системным сервисам

**Цель:** отделить UI от деталей конкретного способа работы с файлами, чтобы браузерный сервер и desktop-приложение могли использовать один и тот же контракт.

**Зависимости:** успешный этап 1 или принятое обновлённое архитектурное решение.

### Задачи

- [ ] Инвентаризировать операции текущего API, которыми пользуются редактор, play mode и MCP.
- [ ] Описать и реализовать узкий контракт сервисов проекта: выбор проекта, list/read/write/rename/delete/query, ошибки и наблюдение за файлами.
- [ ] Добавить адаптер к существующему HTTP API, сохранив текущий браузерный сценарий.
- [ ] Покрыть контрактные операции и граничные случаи тестами на существующей fixture-структуре.
- [ ] Отделить разрешения доступа к файловой системе от UI; операции ограничиваются выбранным проектом и явными разрешениями.
- [ ] Зафиксировать поведение при внешних изменениях файлов, конфликте сохранения, недоступном пути и отказе в доступе.

### Критерии приёмки

- [ ] Основные операции проекта выполняются через единый контракт, а UI не зависит от конкретной реализации транспорта в каждом отдельном месте.
- [ ] HTTP-адаптер сохраняет текущее поведение браузерной версии.
- [ ] Автотесты проверяют успешные операции, ошибки и ограничения доступа.
- [ ] Существующие проекты открываются и сохраняются без изменения формата.
- [ ] Публичные контракты и ограничения задокументированы.

## Этап 3 — нативные операции и сокращение роли Node.js

**Цель:** перенести те системные операции, для которых Tauri/Rust дают измеримое преимущество, не переписывая все сервисы механически.

**Зависимости:** этап 2.

### Задачи

- [ ] Реализовать в Tauri/Rust адаптер для выбранных операций с файловой системой и нативных диалогов.
- [ ] Добавить watcher файлов проекта и безопасную доставку событий в UI.
- [ ] Проверить выдачу проектных файлов и ассетов в play mode через выбранный локальный protocol/serving механизм.
- [ ] Мигрировать API по одной группе операций; сохранять возможность сравнить новое поведение с HTTP-адаптером до приёмки.
- [ ] Зафиксировать судьбу upload/drag-and-drop, логирования, портов и диагностик.
- [ ] Отдельно решить, остаются ли MCP и AI Chat отдельными сервисами. Переписывание их на Rust не считается обязательным без обоснования и PoC.

### Критерии приёмки

- [ ] Перенесённые операции проходят тот же контрактный набор тестов, что и legacy-адаптер.
- [ ] Файловые разрешения не шире необходимого; негативные проверки исключают доступ за пределами разрешённых путей.
- [ ] Сохранение, watcher и play mode не создают циклов обновления и не повреждают файлы.
- [ ] Основной desktop-сценарий не требует установленного пользователем Node.js.
- [ ] Каждый удаляемый endpoint/sidecar имеет подтверждённую замену, обновлённую документацию и тесты.

**Ограничение:** не ставить удаление `server/server.mjs` самоцелью. Сервер удаляется только после переноса всех необходимых контрактов, приёмки браузерного/desktop-сценариев и принятия отдельного решения по MCP/AI.

## Этап 4 — новый workbench и постепенная миграция UI

**Цель:** проверить и внедрять новый UI-каркас по частям, сохраняя работу существующих редакторских подсистем до готовности замены.

**Зависимости:** технические ограничения из этапов 1–2 известны; способ взаимодействия legacy UI и нового workbench выбран по результатам прототипа.

### Задачи

- [ ] Сделать PoC нового workbench на выбранном стеке (кандидаты: Svelte 5, Vite, dockview-core); оценить панели, вкладки, навигацию и сохранение layout.
- [ ] Принять и задокументировать выбор UI-стека, включая критерии отказа от кандидатов.
- [ ] Спроектировать типизированные контракты команд, views, menus, preferences и событий.
- [ ] Мигрировать вспомогательные views по одной: файловое дерево, inspector, outline, стартовая страница, настройки и диалоги.
- [ ] Проверить интеграцию редактора кода; решение о переходе с CodeMirror 5 на CodeMirror 6 принимать на основе требуемых функций и цены миграции.
- [ ] На протяжении перехода сохранить рабочие legacy views либо изолировать их через явно выбранный bridge; не внедрять неподтверждённый «двойной runtime» без прототипа.
- [ ] Сохранить браузерный запуск там, где это входит в поддерживаемый сценарий.

### Критерии приёмки

- [ ] Каждая перенесённая view имеет чек-лист функциональности и тесты по основным сценариям.
- [ ] View можно включить/отключить или сравнить с прежней реализацией до её удаления.
- [ ] Layout, команды, клавиатурная навигация и доступность проверены для целевых сценариев.
- [ ] На согласованной fixture-проектной структуре производительность не хуже зафиксированного baseline; измерение воспроизводимо.
- [ ] Изменения в новых views не ломают Scene Editor, компилятор, сохранение проекта и play mode.

## Этап 5 — отделение Scene Editor и миграция редакторских подсистем

**Цель:** уменьшить зависимость продуктовой логики от Colibri/унаследованного workbench после того, как новая оболочка доказала свою пригодность.

**Зависимости:** этапы 2 и 4.

### Задачи

- [ ] Составить карту зависимостей Scene Editor, сериализаторов, компилятора, моделей и UI-слоя.
- [ ] Отделить сериализацию и генерацию кода от UI-моделей настолько, насколько это необходимо для стабильного контракта.
- [ ] Переносить scene tools и views по вертикальным срезам: выбор/перемещение объекта, свойства, слои, тайлмап, префабы и пользовательские компоненты.
- [ ] Мигрировать Animations Editor, Asset Pack Editor и User Components Editor по отдельным чек-листам.
- [ ] Создать fixture/golden-тесты на открытие, изменение, сохранение, повторное открытие и компиляцию типовых проектов.
- [ ] Удалять конкретные legacy-модули только после того, как их потребители переведены и тесты подтверждают эквивалентное поведение.

### Критерии приёмки

- [ ] Полный основной цикл работает: создать/открыть проект → изменить сцену/префаб/tilemap → сохранить → сгенерировать код → запустить игру → переоткрыть проект.
- [ ] Существующие проектные файлы не теряют поддерживаемые свойства и семантику.
- [ ] Каждый удалённый legacy-модуль имеет описанную замену и подтверждённый набор тестов.
- [ ] Состав оставшегося Colibri/унаследованного кода измерен и задокументирован, а не объявлен отсутствующим только по удалению папки или имени.
- [ ] Лицензионные уведомления сохранены; выводы о необходимости изменения атрибуции оформлены отдельным source/license audit.

## Этап 6 — выпуск desktop-версии и качество продукта

**Цель:** сделать desktop-версию воспроизводимо собираемой, устанавливаемой и диагностируемой до объявления её стабильным пользовательским продуктом.

**Зависимости:** этапы 1–5 в необходимом объёме; конкретный список зависит от принятой архитектуры.

### Задачи

- [ ] Настроить воспроизводимые сборки под заявленные ОС, начиная с Windows.
- [ ] Разделить CI-проверки и release jobs; собирать платформенные артефакты только для поддерживаемых target-ов.
- [ ] Определить модель распространения, подписи приложений и обновлений, каналы публикации и хранение ключей/секретов.
- [ ] Собирать и тестировать установщик на чистом окружении; добавить smoke test запуска/закрытия и открытия fixture-проекта.
- [ ] Добавить диагностику: логи, сообщения ошибок запуска сервисов, восстановление после сбоя и инструкции по сбору отчёта.
- [ ] Задокументировать обновление приложения и восстановление предыдущей версии, если механизм обновлений будет внедрён.

### Критерии приёмки

- [ ] Каждый объявленный target собирается в CI и проходит описанный smoke/acceptance test.
- [ ] Установщик работает на чистом окружении без отдельно установленного Node.js.
- [ ] Артефакт и его версия однозначно связаны с commit/tag; процесс публикации описан.
- [ ] Обновление не включается в релиз до проверки подписи, источника обновлений и сценария отказа.
- [ ] Документация соответствует реально выпускаемым артефактам; ZIP GitHub Actions artifact не называется полноценным релизом или установщиком.

## Долгосрочные направления после стабилизации редактора

Эти идеи пока не являются обязательными критериями текущих этапов. Приоритет и состав должны быть определены отдельными задачами после проверки требований базового продукта.

- **Экспорт игры:** упаковка web-сборки, воспроизводимая структура проекта и инструкции по публикации; затем исследовать desktop/mobile-шаблоны.
- **Ассет-конвейер:** импорт и реимпорт, кэширование, оптимизация и варианты сжатия.
- **Профилирование и отладка:** FPS/память и диагностика игровой сцены, затем исследование точек останова и инструментов runtime.
- **Расширяемость:** публичный SDK только после стабилизации API команд, views, ассетов и жизненного цикла плагинов; затем оценить распространение шаблонов/расширений.
- **Дополнительные runtime:** рассматривать только при наличии конкретного сценария и требований, которые оправдывают абстракцию сверх Phaser.
